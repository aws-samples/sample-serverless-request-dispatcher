Reading of the numbers

  • The dispatcher adds negligible overhead over hand-wiring. At the same memory, sample (annotation dispatcher + Dagger) tracks plain (hand-wired switch) closely: the init p50 gap is ~33 ms at 512 MB and ~38 ms at 1024 MB — smaller than the plain handler's own p50-to-p90 spread. The convenience of annotation routing is effectively free at cold start.
  • SnapStart is the biggest win for the shipped sample. It cuts end-to-end p50 from ~3255 ms (1024 MB) to ~1514 ms, and from ~4816 ms (512 MB) to ~1787 ms, because restore replaces cold JVM + Dagger + SDK init.
  • On-demand priming (primed) does not pay off by itself. It has the highest init p50 (priming front-loads SDK work into init) and only modestly better end-to-end than unprimed sample. Priming is intended to be captured in the SnapStart snapshot — compare primed to snapstart, not to sample.
  • More memory helps on-demand. The sample/plain end-to-end p50 drops ~1500 ms going 512→1024 MB, since more memory also means more CPU during init.
  • minimal is the framework floor (~513–518 ms init), showing how much of a cold start is SDK client construction rather than the dispatcher itself.

Methodology & caveats

  • Workload. Each cold start is one GET /api/products, which runs a DynamoDB Scan. The benchmark table is empty, so the end-to-end figures include a real DynamoDB round trip but no item marshalling or payload transfer. A populated table would add scan and serialization time on top.
  • Cold starts only. Every number here is a first request into a fresh execution environment (or a SnapStart restore). Warm requests reuse an initialized environment and are far faster; they are not measured here.
  • X-Ray tracing is Active. Tracing adds init and per-invoke overhead; these figures include it. A tracing-off configuration would be somewhat faster.
  • Single run, single Region, single architecture. One run on 2026-10-03, us-east-1, x86_64 only. arm64/Graviton was not measured. n = 100 cold starts per cell (99 for primed 1024 MB).
  • Variants run concurrently. The five variants use separate Lambda functions and were driven in parallel. A single Lambda runtime version served every cell (results.json).
  • Two sampling methods. On-demand variants: one configuration update per cold start, so each sample is an isolated fresh environment. SnapStart: one published version per round, then a burst of 25 concurrent invocations of that version; each restore is one sample.
  • Precision. Table values are rounded from results.json (computed by Logs Insights). p50 values recomputed independently from raw/*.csv match within 0.3%.
